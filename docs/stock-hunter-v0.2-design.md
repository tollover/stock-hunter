# Stock Hunter v0.2 設計書

更新日: 2026-11-22
対象: 個人利用 + 家族利用（Cloudflare Accessで許可した利用者のみ）

## 1. 目的と基本方針

Stock Hunterを、商品URLの直接登録とキーワード検索登録の両方に対応する、複数店舗横断の入荷監視・購入管理アプリにする。

- 初期対象店舗は9店舗: Amazon.co.jp、ヨドバシカメラ、ビックカメラ、ヤマダデンキ、Joshin、エディオン、駿河屋、ポケモンセンターオンライン、イオンスタイルオンライン。
- 店舗ごとに取得方法・対応状況・利用条件を分離した「店舗アダプター方式」とする。
- 店舗側の規約、公式APIの利用条件、アクセス制限を優先する。CAPTCHA、待合室、ログイン制限、ボット対策を回避しない。
- 注文確定・決済は必ず利用者本人が販売店で行う。自動購入は実装しない。
- 既存の安全性審査、購入履歴、バックアップ、D1手動同期を壊さない。既存localStorageキーを変更しない。

## 2. 商品登録方法

### A. URL直接登録

入力:
- 商品ページURL（必須）
- 店舗（URLから判定できない場合に選択）
- 優先度（最優先 / 通常 / 低）
- 目標価格（任意）
- メモ（任意）

処理:
1. URLの形式とHTTPSを検証する。
2. 対応店舗ドメインと照合する。未知ドメインは「未対応・要確認」として扱う。
3. 商品名・価格・販売元などは、許可された方法で取得できた項目だけ補完する。
4. 取得できない項目は推測せず「未取得」と表示する。
5. 同一店舗の同一URLは重複登録を防ぐ。
6. 初回状態は「未確認」。登録だけで在庫あり・なしを断定しない。

### B. キーワード検索登録

入力:
- 商品名またはキーワード（必須）
- 対象店舗（複数選択可。初期値は9店舗）
- 優先度
- 価格上限（任意）
- 商品の補足条件（型番、容量、カラー、セット内容等。任意）

処理:
1. 検索条件を「検索ウォッチ」として保存する。
2. 店舗ごとのアダプターが利用可能な公式API・許可された検索機能を確認する。
3. 取得できた検索結果だけを候補一覧に表示する。
4. 利用者が候補を確認して監視商品に追加する。
5. 検索連携が未実装・利用不可の店舗は「検索連携準備中 / 現在検索不可」と明示する。検索できたような架空の結果は出さない。
6. 同じ商品候補が複数店舗にあれば店舗別の商品ページとして保持し、商品名・型番を使って同一商品グループにまとめる。

キーワード検索登録とURL監視登録は別レコードとして保持する。検索ウォッチから見つかった商品は、利用者が選択した後に商品監視へ昇格させる。

## 3. 画面構成

### 商品監視
- 商品名、店舗、販売元、現在価格、目標価格
- 在庫状態: 在庫あり / 在庫なし / 未確認 / 判定不能 / 要確認
- 最終確認時刻、最終成功時刻、次回確認予定
- 優先度、監視状態、エラー・制限表示
- 商品ページを開く操作
- 販売元安全性審査の状態

### 商品登録
タブを2つ設ける:
- 「URLから登録」
- 「キーワードから検索」

検索結果は店舗名、商品名、価格、販売元、商品URL、取得時刻、取得可否を表示。候補選択後に登録確認を行う。

### 店舗・監視設定
- 9店舗の対応状況（利用可能 / 一部対応 / 準備中 / 一時停止）
- 店舗ごとの最短許容確認間隔
- 店舗側のエラー・アクセス制限
- 商品別優先度
- 全体の商品数と店舗別商品数

### 履歴・安全性
- 入荷・価格変化履歴
- 購入履歴
- 販売元審査履歴とブロック記録
- クラウド保存・復元の明確な確認

## 4. 初期容量の目標（性能保証ではない）

初期運用の設計目標は合計約400商品。店舗別の暫定配分:
- Amazon.co.jp: 50
- ヨドバシカメラ: 70
- ビックカメラ: 50
- ヤマダデンキ: 40
- Joshin: 40
- エディオン: 30
- 駿河屋: 70
- ポケモンセンターオンライン: 30
- イオンスタイルオンライン: 20

この配分は実際に監視できる上限ではない。各店舗の許可された取得方法、API上限、ページ構造、Cloudflareの実行時間・リクエスト上限、通知配信量を測定してから店舗別上限を決める。初期目標を満たせない店舗は商品数を自動的に抑制し、未対応を明示する。

## 5. 監視スケジューラー

- Cloudflare Worker + Cron Triggerを候補とする。
- D1に監視対象、店舗アダプター状態、最終確認時刻、次回確認時刻、結果履歴を保存する。
- 1回のCronで全商品を一斉アクセスせず、期限到来した商品を小分けに処理する。
- 店舗単位の同時実行数・レート制限・バックオフを設ける。
- 429、403、CAPTCHA、アクセス拒否、規約上の制限を検出したら自動的に頻度を落とすか停止する。回避策は実装しない。
- 在庫状態は「販売可能の根拠が取れた場合のみ在庫あり」とし、曖昧な表示は判定不能にする。
- 状態変化を検知したときだけ通知し、重複通知を抑制する。

## 6. 通知

- 最初はアプリ内履歴・画面内通知を整備。
- 次にWeb Pushを追加し、iPhoneでは対応するホーム画面追加・通知許可条件を案内する。
- Push購読情報は利用者単位で保存し、家族の端末はそれぞれ登録する。
- 通知には商品名、店舗、確認時刻、検知状態、アプリ内の商品ページへの導線を含める。
- 通知が届かない場合も、アプリ内ログで確認できるようにする。

## 7. データ設計（D1）

既存の stock_hunter_sync は端末バックアップの同期用として維持する。監視サービス用テーブルは別に作る。

想定テーブル:
- users: Accessで認証された利用者
- products: 店舗別商品ページと監視設定
- keyword_watches: キーワード・対象店舗・価格条件
- search_candidates: 検索結果候補と取得時刻
- store_adapters: 店舗別対応状態・制限・最小間隔
- check_jobs: 次回確認時刻・優先度・処理状態
- check_results: 在庫・価格・販売元の確認結果
- alert_events: 入荷・価格変化イベント
- push_subscriptions: 利用者ごとの通知購読情報

個人・家族の共有範囲はCloudflare Accessで許可されたアカウントを基本とし、データの所有者・共有グループを明示する。現在の同期APIはメールアドレス単位で保存するため、家族全員で同じデータを共有する設計にする場合は、グループIDとメンバー認可を追加してから行う。現状の単一メールアカウント共有を家族向け共有機能と誤認させない。

## 8. 安全性と購入フロー

1. 入荷検知
2. 商品・店舗・価格情報の表示
3. 販売元の安全性審査（第三者出品者を含む）
4. リスクまたは未確認なら購入リンクをブロック、または警告して停止
5. 安全性審査を通過した場合のみ商品ページへ移動
6. 注文内容・送料・販売元を本人が確認
7. 最終注文確定・決済は本人が実施

安全性審査は詐欺を100%防止するものではない。取得できない販売元情報を安全と判定しない。

## 9. 実装順序

Phase 1: 既存データを維持した登録画面の再設計
- URL登録 / キーワード検索登録のタブ
- 9店舗マスター
- 検索ウォッチと商品監視商品のデータ区分
- 対応準備中を正直に表示

Phase 2: D1監視データモデルと認証・権限
- 既存の手動バックアップ同期を維持
- 監視用テーブルを追加
- 家族共有の認可モデルを実装

Phase 3: 店舗アダプターを1店舗ずつ検証
- 公式API・許可された方法を優先
- 最初にAmazonと主要量販店を調査
- 実際に取得できた店舗だけ稼働表示

Phase 4: Cronによる分散監視
- 小規模商品数で実測
- 失敗率・平均実行時間・店舗制限を確認
- 問題がなければ段階的に商品数を増加

Phase 5: Web Push通知
- iPhoneで実機確認
- 通知の重複・遅延・失敗を履歴に記録
